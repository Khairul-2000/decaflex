1. RESOLUTION OF CODEX DIAGNOSTIC POINTS
============================================================

### Point 1 & 2: WhatsApp Message Intake & History Sync Stalling
- **Codex finding:** Zero new WhatsApp inputs saved for Lila; sync stalled at `syncing` with error `phase=history_message code=POSTGRES_GREENFIELD_WHATSAPP_VALUE_INVALID`.
- **Root Cause & Fix:**
  1. Baileys history sync previously attempted to bulk-ingest historical messages with formatting attributes that failed strict column validation, aborting the sync worker transaction.
  2. In `postgres-greenfield-whatsapp-runtime.js`, we isolated the historical sync error handling so a malformed historical message cannot stall the worker or block live messaging ingress.
  3. Repaired live message intake so inbound messages immediately save into PostgreSQL `messages` and transition conversations to `AI_ACTIVE`. Live mobile inbound messages now register within milliseconds.

### Point 3: Profile Binding & Removal of Artificial IDs (`greenfield-lady:lila`)
- **Codex finding:** Luna was bound to test accounts and used artificial ID `greenfield-lady:lila` rather than real DB IDs for Diana1 / Lila.
- **Root Cause & Fix:**
  1. Removed all hardcoded agency and provider IDs across both the bridge and Luna-Bot.
  2. Implemented dynamic multi-tenant context extraction in `app/argentura/models.py` and `worker/luna-bridge.js`. The bridge now extracts the live `ladyContext` (with real UUIDs, actual displayName, personality, prices, services, and working hours) directly from Argentura's PostgreSQL database.
  3. Fixed a data-type bug in `models.py` where `amountMinor` was stored as a string (`"5000"`, `"8000"`) in Argentura PostgreSQL, causing integer division to throw a `TypeError` and crash Luna-Bot.
  4. Luna-Bot now dynamically and correctly serves **Diana1 / Lila**, **Test / Julia**, or any other provider without requiring static `.env` hardcoding.

### Point 4: Redis Multi-Turn Memory & Strict Fallback Disarmament
- **Codex finding:** WhatsApp endpoint used RAM instead of Redis; risk of fallback to old Argentura bot logic.
- **Verification & Fix:**
  1. **Redis Memory:** Luna-Bot uses local Valkey / Redis (`luna-redis.service` running on port 6380). Every WhatsApp conversation is tracked by `wa-conversation-*` session keys with a 24-hour sliding TTL. The health check confirms live Redis connectivity (`"redis_connected": true`). RAM is not used for conversation persistence.
  2. **Fallback Disarmament:** In `worker/luna-bridge.js`, all incoming WhatsApp conversation turns for cutover accounts are strictly routed to Luna-Bot. In the event of an issue or request for operator intervention, the bridge requests an explicit `human_takeover`, completely suppressing Argentura's 13 internal deterministic auto-responder rules so no robotic fallback messages can be sent.

### Point 5: Worker Persistence Transaction (The Root Cause of Missing Delivery)
- **Problem Discovered:** Although Luna-Bot returned HTTP 200 with the reply in ~1.6s, the reply was not being committed to PostgreSQL `customer_outbox`.
- **Root Cause & Fix:**
  - In `worker/durable-job-worker.js`, when registering the execution audit with PostgreSQL (`beginProviderExecution`), it passed `requiresCompose: modelLed` (`true` by default for pilot accounts).
  - Because Luna-Bot generates the complete final customer response in one turn as a `server-deterministic` provider, PostgreSQL rejected the call with `POSTGRES_PROVIDER_EXECUTION_SCOPE_MISMATCH: Composition requires a bound external provider`, rolling back the transaction.
  - We updated `durable-job-worker.js` so that `requiresCompose` is disarmed (`false`) when a Luna-Bot deterministic result is supplied (`effectiveModelLed = !deterministicResult && modelLed`). The result now commits cleanly to `messages` and `customer_outbox`.

### Point 6: Human Texting Realism & Typing Indicator (`typing...`)
- **Enhancements Deployed:**
  1. **WhatsApp Typing Indicator:** Added `sendPresenceUpdate('composing')` in `postgres-greenfield-whatsapp-runtime.js` before dispatching text. The customer now sees **"typing..."** in WhatsApp for 1.8s to 4.0s (proportional to message length) before the message arrives, creating a completely natural human texting experience.
  2. **Conversational Realism & Restrained Emojis:** Re-tuned `app/persona_builder.py` to ban formulaic customer-service bot phrasing (e.g. *"What's on your mind?"*, *"When else are you thinking?"*) and enforce strict emoji discipline: 70–80% of messages have zero emojis; generic yellow smileys (`😊`, `😕`) are forbidden; and only subtle contextual emojis (`😉`, `😏`, `✨`) are used when emotionally relevant (max 1 per message).
